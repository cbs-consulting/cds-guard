# cbs CDS Guard

**Nobody changes a protected CDS entity, annotation or code block by accident, on any Git platform.**

---

`cds-guard` protects the parts of a CAP or UI5 project that must not change without the right
people noticing: a CDS entity or a single element, a Fiori annotation, a block of code, a file or
a value in `manifest.json`. You list them in `.guard/protected.yml`, together with who may approve
a change.

`cds-guard lock` stores a fingerprint of each protected item in a lock file. `cds-guard check`
runs in the pull request pipeline and fails when a protected item no longer matches. A deliberate
change updates the lock file, and the lock file can only be merged with approval from the rule's
approvers, through your Git platform's own code owners. No API tokens, no platform-specific code:
the same setup works on GitHub, Azure DevOps, Bitbucket and GitLab.

```text
$ npx cds-guard check
cds-guard: protected items changed.

✗ rule "pricing-model" (Prices and order amounts)
    changed       cds:my.app.Orders.netAmount  content changed
    changed       annotation:my.app.Orders:@UI.LineItem  content changed
  If this change is intended: run "npx cds-guard lock --rule pricing-model", commit the lock file and get approval from @my-org/team-pricing.
```

## ✨ What works where

### What can be protected

| What | Example in `protected.yml` | Counts as a change | Doesn't count |
| --- | --- | --- | --- |
| CDS entity, type, service, aspect | `cds: [ my.app.Prices ]` | elements, types, keys, associations, annotations on it (from any file) | comments, formatting, file moves |
| CDS element | `cds: [ my.app.Orders.netAmount ]` | its type, length, default, annotations | other elements of the entity |
| CDS structure only | `ignoreAnnotations: true` | types and elements | annotations and doc comments |
| CDS annotation | `annotations: [ "my.app.Orders:@UI.LineItem" ]` | the annotation, its qualified variants (`#Compact`) and sub-terms, also when added in another `.cds` file | everything else on the entity |
| Code block | `markers: [ tax-calc ]` | anything between `@protected-begin tax-calc` and `@protected-end`, a removed or extra block | trailing spaces, line endings, code around the block |
| File | `paths: [ "app/*/webapp/annotations/*.xml" ]` | content, a new file matching the pattern, a deleted file | line endings, trailing spaces |
| JSON value | `json: [{ file: …/manifest.json, pointers: [ /sap.app/id ] }]` | the value at the pointer | formatting, other values |

CDS items are compared on the compiled model (CSN) that `@sap/cds` builds, so an `annotate` in
another file is caught and a reformat is not. Markers work in any language that has comments:
`//`, `#`, `/* */`, `<!-- -->`.

### Platforms

| Platform | Pipeline | Approval of lock files | Generated by `cds-guard codeowners` |
| --- | --- | --- | --- |
| GitHub | [`action.yml`](action.yml) | CODEOWNERS + "Require review from Code Owners" | `.github/CODEOWNERS` block |
| Azure DevOps | [`ci/azure-pipelines/cds-guard.yml`](ci/azure-pipelines/cds-guard.yml) | Branch policy "Automatically included reviewers", required, with path filter | `az repos policy required-reviewer` script |
| Bitbucket | [`ci/bitbucket/bitbucket-pipelines.yml`](ci/bitbucket/bitbucket-pipelines.yml) | CODEOWNERS (enforced with a merge check; check your plan) | `CODEOWNERS` block |
| GitLab | [`ci/gitlab/cds-guard.gitlab-ci.yml`](ci/gitlab/cds-guard.gitlab-ci.yml) | CODEOWNERS + "Code owner approval" (Premium) | `CODEOWNERS` block with a `[cds-guard]` section |
| Anything else (Jenkins, …) | [`Dockerfile`](Dockerfile) or `npx cds-guard check` | whatever path-based reviewers the platform has | – |

## 🚀 Quick start

```bash
npm install --save-dev @cbs-consulting/cds-guard # your project already has @sap/cds
npx cds-guard init                               # creates .guard/protected.yml
# add rules to .guard/protected.yml
npx cds-guard lock                               # writes .guard/locks/*.lock
npx cds-guard codeowners --write                 # or --platform azure|gitlab|bitbucket
git add .guard .github/CODEOWNERS && git commit -m "Protect the pricing model"
```

Then add the check to your pipeline and make it required (see [Set up your platform](#-set-up-your-platform)).

## 📝 Configuration

`.guard/protected.yml`:

```yaml
version: 1

cds:
  root: .                    # where the CAP project is (default: the repository root)
  # model: [ db, srv, app ]  # load these folders or files instead of the CAP defaults

# Who must approve changes to the guard itself: .guard/protected.yml and the lock files of
# rules without approvers.
guardOwners: [ "@my-org/leads" ]

# Further files only the guard owners may change, such as the pipeline that runs cds-guard.
guardPaths: [ .github/workflows/cds-guard.yml ]

# Extra glob patterns to skip when looking for files and markers.
ignore: [ "test/**" ]

rules:
  - id: pricing-model
    description: Prices and order amounts
    cds: [ my.app.Prices, my.app.Orders.netAmount ]
    annotations: [ "my.app.Orders:@UI.LineItem", "my.app.Orders:@UI.HeaderInfo" ]
    approvers: [ "@my-org/team-pricing", alice ]

  - id: tax-formula
    markers: [ tax-calc ]
    markerFiles: [ "srv/**/*.js" ]   # where to look (default: all text files)
    approvers: [ bob@example.com ]

  - id: frozen-ui
    paths: [ "app/orders/webapp/annotations/*.xml" ]
    json:
      - file: app/orders/webapp/manifest.json
        pointers: [ /sap.app/id, /sap.ui5/routing ]
```

| Key | Meaning |
| --- | --- |
| `id` | Name of the rule and its lock file `.guard/locks/<id>.lock`. Letters, digits, `.`, `_`, `-`. |
| `cds` | Fully qualified definitions (`ns.Entity`) or elements (`ns.Entity.element`, also nested `ns.Entity.struct.field`). |
| `ignoreAnnotations` | Compare `cds` items without their annotations and doc comments. |
| `annotations` | `target:@Term`, where target is a definition or element. `@UI.HeaderInfo` covers `@UI.HeaderInfo.TypeName` and `@UI.HeaderInfo#Q`. |
| `markers`, `markerFiles` | Marker ids and the glob patterns of files to search. |
| `paths` | Glob patterns of whole files. |
| `json` | Files and [JSON pointers](https://datatracker.ietf.org/doc/html/rfc6901) inside them. |
| `approvers` | Who approves changes, in the format of your platform: `@user`, `@org/team`, e-mail address, or for Azure DevOps e-mail addresses and group names. Without approvers, `guardOwners` approve. |

Changing which items a rule protects needs a new lock (`cds-guard check` reports
`scope-changed`). Changing only `approvers` or `description` does not; run
`cds-guard codeowners --write` instead.

Marker example:

```js
module.exports = function tax (net) {
  // @protected-begin tax-calc
  const rate = 0.19
  return Math.round(net * rate * 100) / 100
  // @protected-end
}
```

## 🔧 Commands

| Command | What it does |
| --- | --- |
| `cds-guard init` | Creates `.guard/protected.yml` with examples. |
| `cds-guard lock [--rule ID]...` | Writes the lock files of all rules, or of the given ones. Refuses items that can't be found. |
| `cds-guard check [--format text\|json\|junit] [--junit FILE]` | Compares with the lock files. Exit code 1 when something changed. |
| `cds-guard codeowners [--platform P] [--write [FILE]] [--branch B]` | Prints or writes the approver entries. Only the block between `# BEGIN cds-guard` and `# END cds-guard` is replaced, the rest of CODEOWNERS stays. |
| `cds-guard list` | Shows every protected item per rule, and which ones can't be found. |

All commands take `--root DIR`. Exit codes: `0` ok, `1` protected items changed, `2` usage or
configuration error.

## 🏗️ Set up your platform

Three things make the guard binding. Without them it is only a warning.

1. **Main only accepts pull requests.** Nobody pushes directly.
2. **The `cds-guard` job is a required check** for merging.
3. **The lock files need approval** from the rule's approvers, through `cds-guard codeowners`.

<details>
<summary><b>GitHub</b></summary>

```yaml
# .github/workflows/cds-guard.yml
name: cds-guard
on: [pull_request, merge_group]
jobs:
  cds-guard:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22 }
      - uses: cbs-consulting/cds-guard@v0
```

In a branch ruleset (or branch protection) for main: "Require a pull request before merging",
"Require review from Code Owners", and "Require status checks to pass" with `cds-guard`. Then
`npx cds-guard codeowners --write`. List the workflow file in `guardPaths` so nobody can switch
the check off unnoticed.
</details>

<details>
<summary><b>Azure DevOps</b></summary>

Copy [`ci/azure-pipelines/cds-guard.yml`](ci/azure-pipelines/cds-guard.yml) into the repository
and reference it from a pipeline (the comment at the top shows how). In the branch policies of
main: add the pipeline as a required **Build validation**. Then create the reviewer policies once:

```bash
npx cds-guard codeowners --platform azure --write   # writes .guard/azure-policies.sh
REPO_ID=$(az repos show --repository my-repo --query id -o tsv) sh .guard/azure-policies.sh
```

Run the script again after approvers change. It adds policies; remove outdated ones in the
branch policy screen.
</details>

<details>
<summary><b>Bitbucket</b></summary>

Merge [`ci/bitbucket/bitbucket-pipelines.yml`](ci/bitbucket/bitbucket-pipelines.yml) into your
pipeline. In the branch restrictions of main: prevent changes without a pull request, and add the
merge checks for successful builds and code owner approval (enforcing merge checks needs Bitbucket
Cloud Premium, or Data Center). Then `npx cds-guard codeowners --platform bitbucket --write`.
</details>

<details>
<summary><b>GitLab</b></summary>

Include [`ci/gitlab/cds-guard.gitlab-ci.yml`](ci/gitlab/cds-guard.gitlab-ci.yml). Turn on
"Pipelines must succeed", protect main with "Allowed to push and merge: No one" and "Code owner
approval" (Premium), then `npx cds-guard codeowners --platform gitlab --write`.
</details>

<details>
<summary><b>Other CI systems</b></summary>

Run `npx cds-guard check` after `npm ci`, or the Docker image without installing anything:

```bash
docker run --rm -v "$PWD:/repo" -w /repo ghcr.io/cbs-consulting/cds-guard check
```
</details>

## ❓ How it works and its limits

- **Fingerprints, not diffs.** Each item is hashed: CDS items as canonical JSON of the compiled
  model without `$location` and other `$` metadata, text as normalised lines. `check` compares the
  working tree with the lock files, so it needs no base branch and works with shallow clones.
- **The project's own `@sap/cds` compiles the model**, so the hashes match what the app builds.
  The lock file records the `@sap/cds` version; after an upgrade, `check` warns if the version
  differs. If the upgrade changes how the model compiles, run `cds-guard lock` and approve it
  like any other change.
- **It is a merge gate, not access control.** Anyone can edit protected code locally. What stops
  the merge is the required check plus the required reviewers on the lock files. People who may
  bypass branch rules can still merge.
- **Renames look like deletions.** A renamed entity is reported as `missing`; update the rule and
  lock again.
